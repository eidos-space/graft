**一条笔记，三个位置**

应用把笔记写入 `app.sqlite`，同时读取 `settings.json` 和 `attachments/` 中的文件。Graft 可以把这些路径选定的版本记录在同一次提交中。

先分清三个位置：

| 位置 | 回答的问题 | 谁改变它 |
| --- | --- | --- |
| 工作区（worktree） | 应用现在读到什么？ | SQLite 事务和普通文件写入 |
| 暂存区（index） | 我为下一次提交选好了什么？ | `graft add`、取消暂存、解决冲突 |
| 历史（history） | 我记录过哪些版本？ | `graft commit` |

```text
应用写入
   |
   v
工作区 -- graft add --> 暂存区 -- graft commit --> 历史
   ^                                                |
   |-------------- 从历史恢复或切换 ----------------|
```

箭头表示捕获、记录或替换。它们不是持续同步。

如果你在 `graft add` 之后又写入一条笔记，下一次提交仍包含之前暂存的数据库。新笔记留在工作区。如果你推送这次提交，远端收到的是已记录的版本。

## 读完后，你应该能判断什么

- 一条命令改变应用文件、暂存内容，还是历史。
- 为什么提交 SQLite 事务不会自动创建 Graft 提交。
- 什么时候使用导出、恢复、fetch 或 pull。
- 遇到冲突或操作中断后，应该检查哪些状态。

[动手练习](/zh/docs/graft-book/hands-on-lab/) 会让你先预测结果，再用 SQL 查询和仓库命令验证。

## 数据库页还有一层存储记录

**仓库提交（repository commit）** 记录一个应用版本：包含哪些路径、各路径的内容，以及父提交。**存储提交（storage commit）** 记录 Graft 存储引擎中的数据库块变化。

二者不同。一次仓库提交可以包含多个数据库和普通文件。暂存数据库时，可能已经产生存储记录，但还没有仓库提交。分支指向仓库提交。

使用 Graft 不需要先理解存储日志编号或页布局。快照章节会在解释复用与重建时介绍它们。

## 精确规则在哪里

本指南解释模型。[任务指南](/zh/docs/guides/track-databases-and-files/) 提供操作步骤。[规范](/zh/docs/specifications/) 定义精确契约与限制。

集成时使用 CLI 及其 JSON 输出、Node.js SDK，或 HTTP 远程服务包。内部存储键、缓存文件名和 Rust 模块边界属于实现细节。
