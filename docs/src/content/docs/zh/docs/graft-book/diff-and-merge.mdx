**改了什么，两边的修改能否合在一起**

路径差异回答“哪些文件变了”。SQLite 逻辑差异回答“哪些受支持的行和表结构条目变了”。

在有两次提交的仓库中：

```bash
graft diff HEAD~1 HEAD
graft diff --rows HEAD~1 HEAD app.sqlite
graft diff --json --rows HEAD~1 HEAD app.sqlite
```

第一条定位变化路径，后两条展开数据库变化。diff 不改变引用、暂存状态、合并记录或已跟踪的工作区文件。

## 行列表为空，不表示数据库没变

数据库也可能因为表结构、索引、虚拟表或其他内容发生变化，而没有普通行修改。

一起检查 `logical_status`、表结构变化、不透明变化、能力与限制。**不透明（opaque）**表示 Graft 无法完整解释该部分变化。应用的审查界面应显示这个限制。

普通表通常使用有符号 64 位 `rowid` 标识行。`WITHOUT ROWID` 表使用声明的主键，包括复合主键。生成列可以显示在输出中，但不会参与普通回放写入。

受支持的布局可以直接读取。其他受支持情况使用隔离的临时兼容数据库，并报告 `materialized_compat`。这个临时数据库不是应用工作区。

## 合并比较三个版本

假设两个分支从相同的笔记开始：

| id | Base 内容 | Ours 内容 | Theirs 内容 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | first | first, edited locally | first | 保留本地修改 |
| 2 | second | second | second, edited remotely | 保留传入修改 |

两边修改了不同行。受支持且通过验证的合并可以保留两项修改。

如果两边对第 1 行做了不兼容的修改，Graft 会报告冲突，让你选择结果。

```text
          Base：共同祖先
          /            \
 Ours：本地 HEAD     Theirs：目标版本
          \            /
              合并结果
```

图中表示历史关系与输入。合并使用行和表结构的含义，不比较存储 LSN 的数值大小。

## 先判断历史关系

| 关系 | 结果 | 发生什么 |
| --- | --- | --- |
| 目标已经在本地历史中 | 已是最新 | 不改变状态 |
| 本地 HEAD 是目标的祖先 | 快进（fast-forward） | 移动到目标并检出内容 |
| 两边都有新提交 | 三方合并（three-way） | 组合变化或进入冲突状态 |

无共同历史时，使用空基准，并报告 `merge_base = null`。

SDK 把只读的 `planMerge` 与 `applyMerge` 分开。计划令牌绑定观察到的输入与策略。状态变化后，apply 会拒绝过期计划。

## 自动合并的边界

Graft 对兼容的 SQLite 输入尝试行与表结构合并。它构建私有候选，在事务中应用安全变化，再验证结果，包括约束与外键。

不兼容的行修改、冲突的表结构、不受支持的 SQLite 内容，以及修改与删除相遇，都可能需要解决冲突。普通文件采用保守的整路径冲突。表结构和内部解析器是有限的内置集合，不是任意 SQL 钩子。

“修改了不同行”有助于预测，但不是无条件保证。表结构兼容性和约束仍然影响结果。

## 完成或中止三方合并

对已经创建并提交过的分支：

```bash
graft --db app.sqlite merge feature/notes
graft status
graft --db app.sqlite conflicts --json
```

执行会写回工作区的操作前，关闭受影响的应用连接。

如果三方合并已没有未解决冲突：

```bash
graft merge --continue -m "merge notes"
```

快进已经移动到目标，不需要继续创建合并提交。

如果仍有冲突，按[冲突指南](/zh/docs/guides/merge-conflicts/)检查并解决，再继续。若要丢弃当前合并结果并恢复合并前版本：

```bash
graft merge --abort
```

冲突状态包含暂存阶段和持久化的解决记录。重启应用不会自动解决冲突。中断后应检查这些状态，继续解决或中止。

成功继续会创建同时以 Ours、Theirs 为父提交的提交。中止只有在恢复成功后才清除合并记录。
