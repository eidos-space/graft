**下一次提交会包含哪些修改**

SQLite 事务保存应用数据。`graft add` 选定一份快照。`graft commit` 把选定的版本记录到仓库历史。

这是三个独立动作。

## 跟随一条笔记观察变化

假设 HEAD 中有一条笔记。

| 动作 | 工作区 | 暂存的数据库 | HEAD |
| --- | --- | --- | --- |
| 用 SQLite 插入第二条笔记并提交事务 | 两条笔记 | 没有暂存变化 | 一条笔记 |
| `graft add app.sqlite` | 两条笔记 | 两条笔记的快照 | 一条笔记 |
| 用 SQLite 插入第三条笔记并提交事务 | 三条笔记 | 仍是两条笔记 | 一条笔记 |
| `graft commit -m "save two notes"` | 仍是三条笔记 | 已提交的暂存变化被清除 | 两条笔记 |

第三条笔记仍是未暂存变化。commit 使用暂存内容，不会再次捕获当前数据库。

如果希望包含第三条笔记，提交前再次执行 `graft add app.sqlite`。

## 初始化、暂存、检查、记录

`graft init` 创建 `.graft/` 和初始分支位置。它不会创建数据库，也不会自动跟踪现有文件。

在已有应用目录中：

```bash
graft init
graft status
graft add app.sqlite
graft add settings.json
graft diff --staged
graft diff --rows --staged app.sqlite
graft commit -m "save notes and settings"
graft status
```

提交前检查暂存差异。提交后的 status 会告诉你是否还有更新的工作区变化。

使用 `graft add --all` 可以一起暂存符合条件的新增、修改和删除。忽略规则与路径选择见[跟踪数据库与文件](/zh/docs/guides/track-databases-and-files/)。

## 不同文件如何进入同一次提交

数据库经过一致快照捕获；普通文件读取精确的字节内容。

```text
app.sqlite ------ 一致捕获 --> 数据库快照 ------+
settings.json --- 读取字节 --> 文件 blob -------+--> 暂存区
report.pdf ------ 读取字节 --> 外部载荷指针 -----+
                                                  |
                                                  | commit
                                                  v
                                               应用版本
```

一次提交把 HEAD 中的树与暂存的替换、删除组合起来。未暂存的路径沿用 HEAD 中已记录的版本。

共同的提交提供版本边界，但不会把各路径的独立捕获变成一个事务。需要这种保证时，应用必须协调相关写入。

## 为什么最后才移动分支

Graft 先写入所需的不可变对象，再把分支移动到新提交。否则，分支可能指向内容尚不可用的版本。

引用更新前失败，可能留下不可达对象，但分支仍指向旧版本。如果后续步骤失败，先检查状态和历史，再判断提交是否已发生。

这种顺序不保证完整的崩溃持久性。部分对象、暂存区和合并记录仍直接写入，1.0 不承诺端到端的 `fsync` 契约。引用日志追加与引用替换也是独立操作。

## 验证你的判断

你暂存了两条笔记，又插入第三条，然后提交。HEAD 中有几条？

**两条。** 导出 HEAD 并查询即可验证。[动手练习](/zh/docs/graft-book/hands-on-lab/) 会执行这个实验。

commit 写入本地历史。上传历史需要另外执行 [push](/zh/docs/graft-book/remotes-and-recovery/)。
