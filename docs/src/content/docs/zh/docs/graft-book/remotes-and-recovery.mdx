**哪个版本会到达远端**

远端保存已经记录的仓库历史，以及读取历史所需的内容。它不会监听应用的实时数据库。

| 动作 | 本地历史 | 远端历史 | 工作区 |
| --- | --- | --- | --- |
| SQLite 事务 | 不变 | 不变 | 改变数据库 |
| add 和 commit | 记录选定版本 | 不变 | 保留当前文件 |
| push | 保留本地版本 | 发布已记录历史 | 不替换文件 |
| fetch | 下载历史，更新远端跟踪引用 | 读取 | 不替换文件 |
| pull | 先 fetch，再合并 | 读取 | 可能替换文件 |
| clone | 从远端创建本地仓库 | 读取 | 写入检出的文件 |

仅仅执行 push，不会让未提交的笔记进入远端历史。

## 试用文件系统远端

先在 `main` 上创建一次提交，再为独立的测试远端选择绝对路径：

```bash
graft remote add origin fs:///tmp/graft-book-remote
graft push origin main
graft ls-remote origin
```

隔离测试应选择新的远端路径。Graft 也支持对象存储和 HTTP 远端，见[远端后端](/zh/docs/remotes/)。

远端提供另一份历史副本。备份仍需要独立的保留、访问和恢复策略。

## 先上传内容，最后更新分支

远端分支应指向所需内容已经发布的版本。

```text
上传数据库存储与外部文件载荷
              |
上传描述版本的仓库对象
              |
有条件地更新远端分支
```

最后一步使用**比较并交换（CAS）**：只有分支仍等于开始时观察到的值，才执行更新。

如果另一个客户端已经移动分支，更新会失败。已上传的不可变内容可能暂时不可达，但分支不会暴露这次未完成的发布。

强制推送放宽快进规则，仍会通过 CAS 检查远端的预期值。

## fetch 让你先检查，pull 还会应用变化

fetch 下载选定历史，并更新 `origin/main` 这样的远端跟踪引用。它不移动当前分支、不改变暂存区，也不替换已跟踪文件。

```bash
graft fetch origin main
graft log
graft diff HEAD origin/main
```

最后一条比较本地版本与刚获取的远端位置。

pull 执行 fetch、合并规划和合并应用。它可能快进、进入冲突状态，并替换数据库。先关闭受影响的应用连接。

元数据可能先于全部历史页或外部载荷到达。后续读取可以补齐缺失内容。“能看到提交”与“所有字节都已在本地”是两种状态。

clone 初始化新仓库，获取远端历史，设置跟踪关系，再检出文件。它不会静默覆盖非空目标目录。

## 响应丢失时，结果可能未知

分支更新请求已发送，但响应丢失时，服务端可能已经执行。超时或取消不能证明服务端没有动作。

重新读取远端分支：

| 观察到的值 | 含义 |
| --- | --- |
| 预期的新提交 | 当前分支已处于预期位置 |
| 原提交 | 当前引用未体现预期更新 |
| 其他提交 | 需要处理其他写入者或历史分歧 |

必要时 fetch 最新状态并重新规划。不要直接发布另一个后继版本。

## 根据仍有效的状态恢复

| 失败 | 先检查什么 |
| --- | --- |
| 捕获或暂存失败 | 工作区与已有暂存状态 |
| 提交报告失败 | 当前引用、历史与暂存区 |
| 切换或恢复中途停止 | 状态、返回的路径动作与受影响文件 |
| 合并中断 | 暂存区冲突阶段与解决记录 |
| push 响应丢失 | 远端分支值 |

如果恢复可能替换文件，先停止应用写入并关闭受影响的 SQLite 连接。检查 `graft status --json`，完成或中止活跃合并，确认不确定的远端结果，再恢复写入。

缺失或损坏的内容必须报告。缺失页不能当作全零页，缺失载荷不能当作空文件。

## 清理是独立操作

SQLite 存储垃圾回收、外部载荷清理与仓库对象维护有不同的根和限制。1.0 集成面没有公开的松散对象垃圾回收操作。

不要通过删除内部存储来处理未完成合并或不确定的推送。先恢复有效版本，再使用对应维护命令。

精确的发布与恢复规则见[远端和仓库规范](/zh/docs/specifications/)。
