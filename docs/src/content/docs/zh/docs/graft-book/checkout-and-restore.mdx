**你想查看旧版本，还是使用旧版本**

如果只想检查旧数据库，同时让应用继续使用当前版本，先**导出（export）**到独立路径。

如果希望应用使用历史内容，**恢复（restore）**一个路径或**切换（switch）**分支。这些操作可能替换工作区文件。

| 动作 | 内容写到哪里 | 对应用文件的影响 |
| --- | --- | --- |
| 补齐内容（hydration） | 本地 Graft 存储 | 下载缺失内容，不替换已跟踪文件 |
| 导出（export） | 独立输出路径 | 保留工作区数据库 |
| 实体化（materialization） | 已跟踪的工作区路径 | 把已记录内容写回该路径 |

**实体化**指把记录的内容写成工作区文件。切换、checkout、恢复、hard reset、pull、clone 和部分合并操作都可能执行它。

## 先导出，再检查

在已跟踪 `app.sqlite` 的仓库中：

```bash
graft export --source HEAD~1 --output ../previous.sqlite app.sqlite
sqlite3 ../previous.sqlite 'SELECT * FROM notes ORDER BY id;'
```

选择工作区外尚未使用的输出路径，避免导出文件成为新的应用文件候选。导出不移动 HEAD，也不改变暂存区。

## 恢复已记录的路径

先关闭应用对这个数据库的连接，再执行：

```bash
graft restore --source HEAD -- app.sqlite
graft sql --db app.sqlite "SELECT * FROM notes ORDER BY id;"
graft status
```

这会从 HEAD 恢复该路径，不移动分支。该路径的工作区变化会被替换。显式指定 `--source HEAD` 很重要：没有指定来源时，工作区恢复使用暂存内容。

取消暂存是另一种操作：

```bash
graft restore --staged -- app.sqlite
```

它从 HEAD 重置暂存条目，保留工作区数据库。

## 替换前关闭连接

替换后，即使连接处于空闲状态，也可能继续引用旧文件。检查写入锁不能代替应用管理连接生命周期。

采用以下顺序：

```text
暂停新的应用写入
        |
完成事务，关闭受影响的 SQLite 连接
        |
执行会替换文件的操作
        |
检查操作结果与仓库状态
        |
重新连接到结果文件
```

Graft 会检查 SQLite 替换条件，并处理 WAL 附属文件。活跃写入者、忙碌的 WAL、无效附属文件或路径冲突都可能阻止替换。先处理报告的问题，再重试。

## 一次重命名不等于多文件事务

Graft 使用临时文件和受保护的替换。多路径 checkout 可以使用备份，并在失败后尝试恢复。但每个替换独立执行，操作系统错误可能留下部分效果。

失败后检查 `graft status`、返回的路径动作和受影响的数据。确认结果后再恢复应用写入。不要根据一个文件推断整个操作的结果。

## 集成时检查操作效果

SDK 的 `operationMaterializesWorktree(name)` 是调用前的保守判断：返回 `true` 表示这类操作在某些输入下可能替换已跟踪路径。结果中的 `worktree_paths` 报告实际受影响的路径。

| 操作 | 可能替换已跟踪的工作区文件吗？ |
| --- | --- |
| status、log、diff、fetch、add、commit | 否 |
| 取消暂存、mixed reset | 否 |
| switch、checkout、路径恢复、hard reset、pull、clone | 是 |
| 合并规划（`planMerge`） | 否，但可能补齐所需内容 |
| 应用合并、解决冲突、中止合并 | 是 |
| export | 否，它写入独立目标 |

这里的“否”表示不替换已跟踪的应用文件。fetch 仍会写入仓库存储，commit 仍会写入对象和引用。

`worktree.materialize_sqlite = false` 关闭普通 checkout 计划中的 SQLite 投影。显式冲突解决和普通文件仍可能写入工作区。管理连接时应使用操作判断。

分支和 reset 命令见[历史与恢复](/zh/docs/guides/history-and-restore/)，精确替换规则见[工作区规范](/zh/docs/specifications/)。
