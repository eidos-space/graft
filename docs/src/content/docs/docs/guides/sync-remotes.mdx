---
title: Sync with Remotes
description: Send recorded history to a remote, fetch for inspection, and understand when pull replaces local files.
---

A remote stores recorded history and its required database and file content outside the local `.graft/` directory. Push transfers commits, not the application's latest uncommitted changes.

For the opt-in native password-based transport, see [Encrypted Sync](/docs/guides/encrypted-sync/).

## Choose the action before the backend

| Goal | Command | Replaces tracked files? |
| --- | --- | --- |
| Publish local commits | `graft push origin main` | No |
| Obtain remote history for inspection | `graft fetch origin main` | No |
| Obtain and apply remote history | `graft pull origin main` | Can |
| Start a new local repository | `graft clone <uri> main` | Writes checked-out files |

Close affected application SQLite connections before pull. After conflicts or failure, inspect repository state before reopening them.

## 1. Configure a remote

For an isolated local test, choose a fresh absolute path:

```bash
graft remote add origin fs:///tmp/graft-remote
graft remote list
```

`origin` is a local name for the remote. It is not a branch.

For S3-compatible storage:

```bash
export AWS_ACCESS_KEY_ID="..."
export AWS_SECRET_ACCESS_KEY="..."
export AWS_REGION="auto"
graft remote add origin 's3_compatible://my-bucket/prod/app?endpoint=https://account.r2.cloudflarestorage.com'
```

For a Graft HTTP service:

```bash
export GRAFT_REMOTE_TOKEN='grt_...'
graft remote add origin 'https://example.com/acme/archive'
```

These are alternative configurations. Keep credentials in explicit environment or adapter inputs, not URL values or repository configuration.

To use a different token variable:

```bash
export GRAFT_ARCHIVE_TOKEN='grt_...'
graft remote add origin 'https://example.com/acme/archive?token_env=GRAFT_ARCHIVE_TOKEN'
```

The query names a variable; it does not contain the token.

Supported URI families include `memory`, `fs://`, `s3://`, `s3_compatible://`, HTTP(S), and the explicit `graft+http(s)://` form. See [URI rules](/docs/reference/remote-uris/).

## 2. Publish a recorded version

Start with a commit on `main`:

```bash
graft status
graft push origin main
graft ls-remote origin
```

**Check:** the remote branch names the intended commit. Unstaged or staged changes remain local until committed.

Graft uploads required immutable content before updating the remote branch. The branch update checks the previously observed value, so a concurrent writer can cause rejection.

To push all local branches:

```bash
graft push --all origin
```

`graft push --force origin main` permits a deliberate non-fast-forward update. It still uses expected-value checks and can change history visible to other clients.

## 3. Fetch, inspect, then decide whether to apply

```bash
graft fetch origin main
graft diff HEAD origin/main
```

**Check:** your branch and worktree remain in place; the diff shows how the fetched remote version differs.

To fetch all branches:

```bash
graft fetch --all origin
```

When ready to apply the remote branch:

```bash
graft pull origin main
graft status
```

Pull can fast-forward or enter a three-way merge. If conflicts remain, use the [conflict guide](/docs/guides/merge-conflicts/). Do not treat a completed download as a completed merge.

Once a branch has a configured upstream, `graft push` and `graft pull` can use it without explicit names.

## 4. Clone into a new directory

```bash
mkdir app-clone
cd app-clone
graft clone fs:///tmp/graft-remote main
graft status
graft log
```

Clone configures `origin`, obtains the branch, and materializes its recorded files. Use an empty destination.

**Check:** confirm the branch and commit, then query the restored application database.

## If a push response is lost

Timeout or cancellation after dispatch does not prove the remote update failed. Read the remote branch again and reconcile its value before publishing another successor.

A remote copy is part of a backup strategy, but does not define retention or recovery policy. See [remotes and recovery](/docs/graft-book/remotes-and-recovery/) for failure boundaries, and [HTTP integration](/docs/guides/http-remote/) for service requirements.

Manage configured remotes with `remote get-url`, `set-url`, `rename`, `remove`, and `prune`; exact arguments are in the [CLI reference](/docs/reference/cli/).
