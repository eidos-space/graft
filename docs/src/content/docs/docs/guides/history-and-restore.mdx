---
title: History and Restore
description: Choose the operation that changes files, staging, or branch position, then verify the result.
---

Decide what you want to change before choosing a history command.

| Goal | Operation | Effect |
| --- | --- | --- |
| Record selected changes | Add, then commit | Creates local history |
| Inspect an old database separately | Export | Writes an independent file |
| Replace one current file | Restore with an explicit source | Changes that worktree path |
| Remove a staged selection | Restore staged | Leaves application files in place |
| Use another branch | Switch | Changes branch and can replace tracked files |
| Move the current branch backward | Reset | Effects depend on the reset mode |

Close affected application SQLite connections before operations that replace files. See [replacement lifecycle](/docs/graft-book/checkout-and-restore/).

## Record and inspect a checkpoint

```bash
graft status
graft add --all
graft diff --staged
graft commit -m "save checkpoint"
graft log
graft show HEAD
```

Commit records staged content. Newer changes made after `add` remain in the worktree. Use `--json` on status, log, and show for integrations.

## Inspect an older database without replacing it

Use a fresh destination outside the worktree and query it with `sqlite3`:

```bash
graft export --source HEAD~1 --output ../previous.sqlite app.sqlite
sqlite3 ../previous.sqlite 'SELECT * FROM notes ORDER BY id;'
```

**Check:** the output database contains the old rows; your application database remains in place.

## Restore one path

These commands assume the paths exist in the selected source:

```bash
graft restore --source HEAD -- app.sqlite
graft restore --source HEAD~1 -- attachments/report.pdf
```

The selected worktree content is replaced. The branch position does not move. Without `--source`, worktree restore uses the index.

**Check:** query or open the restored path, then run `graft status`. Restoring an older version may leave a change relative to current HEAD; commit it if you want a new version recording that restoration.

To cancel staging while keeping worktree content:

```bash
graft restore --staged -- app.sqlite
graft restore --staged --all --kind sqlite_database
```

## Create and use branches

```bash
graft branch experiment
graft switch experiment
```

Creating a branch adds a pointer to the current version. Switching changes the current branch and checks out its tracked content.

To create and switch in one command:

```bash
graft switch -c feature/notes main
```

List local, remote, or all branches:

```bash
graft branch
graft branch -r
graft branch -a
```

**Check:** confirm the selected branch, then query the database to verify its content.

## Checkout a revision

```bash
graft checkout HEAD~1
```

This selects the older commit directly, producing a detached HEAD. To return to a branch, use `graft switch main`.

For a single path:

```bash
graft checkout HEAD~1 app.sqlite
```

Use restore when you want to specify the source and destination state explicitly.

## Choose a reset mode

Reset moves the current branch to the target. It rewrites that branch's visible position rather than adding a restoration commit.

| Mode | Branch position | Staged state | Worktree |
| --- | --- | --- | --- |
| `--soft` | Moves | Keeps current selection | Keeps current files |
| `--mixed` | Moves | Resets to target | Keeps current files |
| `--hard` | Moves | Resets to target | Replaces with target content |

Example commands are alternatives, not a sequence:

```bash
graft reset --soft HEAD~1
graft reset --mixed HEAD~1
graft reset --hard HEAD~1
```

Hard reset discards staged and unstaged changes. Use it only when replacement is intended.

## Name a version with a tag

```bash
graft tag checkpoint-1
graft tag -a reviewed-1 -m "reviewed checkpoint"
graft tag
```

The first creates a lightweight tag; the second records an annotated tag. A tag lets you refer to a version by name.

After any failed replacement, inspect status and affected paths before resuming application writes. Multi-path replacement is not a filesystem-wide transaction.
