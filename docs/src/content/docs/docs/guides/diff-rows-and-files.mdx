---
title: Diff Rows and Files
description: Select two states to compare, then interpret path, row, schema, and unsupported changes.
---

A diff has two questions: **which states are being compared**, and **how much content should be interpreted**.

Start by selecting the states:

| Question | Command | Comparison |
| --- | --- | --- |
| What changed after staging? | `graft diff` | Index to worktree |
| What will I commit? | `graft diff --staged` | HEAD to index |
| What changed between versions? | `graft diff HEAD~1 HEAD` | First parent to current commit |
| How do branches differ? | `graft diff main experiment` | Main to experiment |

The direction matters: inserts and deletes describe the changes from the first state to the second. These commands inspect state without changing refs, the index, merge records, or tracked files.

## 1. Locate changed paths

```bash
graft diff HEAD~1 HEAD
graft diff --json HEAD~1 HEAD
```

Path output identifies additions, deletions, and modifications. It also reports `kind` (database, text, or binary) and `storage` (snapshot, inline, or external).

To select one recorded database:

```bash
graft diff HEAD~1 HEAD app.sqlite
```

To select a content class:

```bash
graft diff --kind sqlite_database
graft diff --kind text_file
graft diff --kind binary_file
```

## 2. Expand database changes

Add `--rows`:

```bash
graft diff --rows HEAD~1 HEAD app.sqlite
graft diff --json --rows HEAD~1 HEAD app.sqlite
graft diff --rows --staged app.sqlite
```

If the second version adds note 2, expect an inserted row. If it edits note 1, expect an update with old and new values.

The database result can include schema changes, row changes, opaque changes, capabilities, and limitations. An empty row list does not establish that the whole database is unchanged.

## 3. Read logical status with the details

| `logical_status` | What it tells you | Review treatment |
| --- | --- | --- |
| `logical_changes` | Supported row or schema changes were found | Show those changes and any accompanying limitations |
| `unsupported_logical_surface` | Graft cannot fully interpret changed SQLite content | Keep the caveat visible and allow file-level review |
| `file_changed_no_supported_logical_changes` | Bytes changed without a net change in supported logical content | Describe the file change without inventing row edits |
| `row_diff_unavailable` | Row analysis is unavailable for that file | Use path-level information |

**Check:** read schema and opaque changes together with row changes. For a binary attachment, use path metadata and an appropriate file viewer.

## Compare two independent SQLite files

Use `--no-index` when you have database files rather than repository revisions:

```bash
graft diff --no-index old.sqlite new.sqlite
graft diff --no-index --rows old.sqlite new.sqlite
graft diff --no-index --rows --json old.sqlite new.sqlite
```

This accepts exactly two regular SQLite files and does not require a repository. Each is captured consistently, including committed WAL content.

Default output compares physical snapshots. `--rows` expands logical schema, table, row, and opaque changes. Repository selectors such as `--staged`, `--root`, `--kind`, and `--content` do not apply.

## Use the right boundary in an application

Use `--json` for integrations. Show path summaries for navigation and logical details for a selected database. Preserve capability and limitation fields rather than showing every empty row list as “no changes.”

Use repository commit IDs, branches, and tags for user-visible history. A storage LSN belongs to a specific storage log and is not a global application version.
