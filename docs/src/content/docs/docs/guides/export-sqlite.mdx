---
title: Export SQLite Files
description: Inspect a recorded database in an independent file without replacing application data.
---

Use export when you want to inspect or hand off a database version while keeping the current application database in place.

Export writes an ordinary SQLite file to an independent destination. It does not move HEAD, change the index, or replace the tracked database.

## Export an explicit version

From a repository tracking `app.sqlite`, choose fresh output paths outside the worktree:

```bash
graft export --source HEAD --output ../notes-head.sqlite app.sqlite
graft export --source HEAD~1 --output ../notes-previous.sqlite app.sqlite
```

`HEAD` selects the current recorded version. `HEAD~1` selects its first parent. Specify the source when you need a particular historical checkpoint.

For structured results:

```bash
graft export --json --source HEAD --output ../notes-review.sqlite app.sqlite
```

The output describes an exported file, not a live connection to Graft storage.

## Query the result with ordinary SQLite tooling

```bash
sqlite3 ../notes-head.sqlite 'SELECT id, body FROM notes ORDER BY id;'
```

**Check:** compare the query result with the version you intended to export. Your worktree may contain newer unstaged notes, so querying it can produce a different result.

Use `sqlite3` or another ordinary database viewer for the independent file. `graft sql` operates on databases in a Graft worktree.

## Choose restore when the application should use that version

Export keeps the current tracked file. Restore replaces it:

```bash
graft restore --source HEAD -- app.sqlite
```

Close affected application SQLite connections before restore. Query the resulting database and inspect status before resuming writes.

Switch, checkout, pull, and merge operations can also write recorded database content to worktree paths. Staging and commit do not replace the live database.

## Record edits made by another SQLite tool

For a tracked database with a `notes` table:

```bash
sqlite3 app.sqlite "INSERT INTO notes(body) VALUES ('external edit');"
graft add app.sqlite
graft commit -m "record external edit"
```

Commit the SQLite transaction before staging. Graft captures committed WAL content without requiring a manual checkpoint, then reuses unchanged 4 KiB storage chunks.

## Configure checkout projection only when needed

```toml
[worktree]
materialize_sqlite = true
```

The default is `true`. Setting it to `false` disables SQLite projection in ordinary checkout plans. It does not make every operation read-only: explicit conflict resolution and ordinary file artifacts can still write the worktree.

Use the SDK operation gate and actual path results to manage database connections. See [checkout and restore](/docs/graft-book/checkout-and-restore/) for the lifecycle and failure limits.
