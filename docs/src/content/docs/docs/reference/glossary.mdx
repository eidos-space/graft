Use this page when a term blocks your reading. The [architecture guide](/docs/graft-book/) explains how these pieces work together.

## Current files and recorded versions

| Term | Meaning | Example |
| --- | --- | --- |
| Application state | Durable data the application needs to open coherently | Notes database, settings, and referenced attachments |
| Worktree | Directory of current application files | `project/app.sqlite` is the database the application opens |
| Repository | Worktree plus Graft state in `.graft/` | Files, history, staged changes, storage, and recovery records |
| Index / staging area | Selected changes for the next commit | A two-note snapshot staged before a third note was written |
| Repository commit | Immutable record of a version's tree and parent commits | The version created by `graft commit` |
| Tree | Mapping from repository paths to recorded content | `app.sqlite`, `settings.json`, and an attachment |
| Blob | Repository object describing one path's content | Database snapshot descriptor or file content |
| Ref | Mutable pointer to an object | Branch `main` points to its current commit |
| HEAD | Current branch position or a directly selected commit | Normally follows `main`; can be detached |
| Snapshot | Immutable, consistent committed database state | The database captured by `graft add app.sqlite` |

## File content and storage

| Term | Meaning |
| --- | --- |
| Artifact | A tracked ordinary file rather than a SQLite database, such as `settings.json` |
| External payload | File bytes stored separately and identified by content hash; a pointer describes them |
| Kind | Content classification: `sqlite_database`, `text_file`, or `binary_file` |
| Storage | Representation: `sqlite_snapshot`, `inline`, or `external` |
| Storage commit | Record of changed 4 KiB chunks inside the storage engine; distinct from a repository commit |
| LSN | Sequence number within one storage log; comparable only inside that log |

Kind and storage answer different questions. A JSON file can be `text_file` with `external` storage.

## Getting recorded content to a destination

| Term | Meaning | Changes tracked worktree files? |
| --- | --- | --- |
| Hydration | Obtain missing immutable content in local Graft storage | No |
| Export | Write a recorded database to an independent destination | No |
| Materialization | Write recorded content to tracked worktree paths | Yes |
| Remote | Named backend that stores history and required content outside the local repository | Connecting one does not; pull can |

## Combining versions

| Term | Meaning |
| --- | --- |
| Base | Common ancestor used for a three-way merge; an empty base when histories are unrelated |
| Ours | Local HEAD observed when the merge is planned |
| Theirs | Target revision being merged |
| Fast-forward | Move to a descendant version when the local history has not diverged |
| Conflict | A change for which Graft needs an explicit resolution |
| Opaque change | Changed SQLite content Graft cannot fully interpret |
| CAS / compare-and-swap | Update a mutable pointer only if it still equals an expected value |

Saving a SQLite transaction, recording a Graft commit, and synchronizing history are separate operations. When a guide says “commit,” check which of the first two it means.
