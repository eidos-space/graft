---
title: 07 Hands-On Lab
description: Predict and verify how staging, commit, export, branch switching, and restore affect one notes database.
---

**Predict first, then query the result**

This lab checks the three-place model: worktree, index, and history. It uses real local commands, not a simulation.

You need the [Graft CLI](/docs/overview/installation/) and `sqlite3` to query the exported database. Run the commands in a new scratch directory. Each `graft sql` call opens and closes its own database connection; close any other application connections before switching or restoring.

## 1. Record one note

```bash
mkdir graft-book-lab
cd graft-book-lab
graft init
graft sql --db app.sqlite \
  "CREATE TABLE notes(id INTEGER PRIMARY KEY, body TEXT NOT NULL);"
graft sql --db app.sqlite \
  "INSERT INTO notes VALUES (1, 'first');"
printf '{"theme":"paper"}\n' > settings.json
graft add app.sqlite
graft add settings.json
graft commit -m "save first note"
graft status
```

**Check:** status is clean. HEAD records one note and the settings file.

## 2. Stage two notes, then write a third

Before committing, predict how many notes the commit will contain.

```bash
graft sql --db app.sqlite "INSERT INTO notes VALUES (2, 'second');"
graft add app.sqlite
graft sql --db app.sqlite "INSERT INTO notes VALUES (3, 'third');"
graft diff --rows --staged app.sqlite
graft diff --rows
graft commit -m "save two notes"
```

**Check:** the staged diff shows the second note. The unstaged diff shows the third. Commit records the staged two-note snapshot.

## 3. Compare recorded and live content

Export to a fresh path outside the worktree:

```bash
graft export --source HEAD --output ../graft-book-head.sqlite app.sqlite
sqlite3 ../graft-book-head.sqlite 'SELECT id, body FROM notes ORDER BY id;'
graft sql --db app.sqlite "SELECT id, body FROM notes ORDER BY id;"
graft status
```

**Check:** the exported database contains rows 1 and 2. The worktree contains rows 1, 2, and 3. Status reports the remaining worktree change.

If both queries return three rows, check whether you ran `add` again after inserting the third note.

## 4. Record the third note and compare commits

```bash
graft add app.sqlite
graft commit -m "save third note"
graft diff --rows HEAD~1 HEAD app.sqlite
graft log
```

**Check:** the diff reports insertion of row 3. HEAD now records three notes.

## 5. Change a branch and switch back

Predict whether creating a branch changes the live note.

```bash
graft branch experiment
graft sql --db app.sqlite "SELECT body FROM notes WHERE id=1;"
graft switch experiment
graft sql --db app.sqlite "UPDATE notes SET body='edited on experiment' WHERE id=1;"
graft add app.sqlite
graft commit -m "edit first note"
graft switch main
graft sql --db app.sqlite "SELECT body FROM notes WHERE id=1;"
graft switch experiment
graft sql --db app.sqlite "SELECT body FROM notes WHERE id=1;"
```

**Check:** branch creation leaves the note unchanged. On `main`, row 1 is `first`. On `experiment`, it is `edited on experiment`. Switching installs the selected version's database.

## 6. Replace an unrecorded edit

The following deletion affects only this scratch database:

```bash
graft sql --db app.sqlite "DELETE FROM notes WHERE id=3;"
graft status
graft restore --source HEAD -- app.sqlite
graft sql --db app.sqlite "SELECT id, body FROM notes ORDER BY id;"
graft status
```

**Check:** row 3 returns and status is clean. Restore replaced the unrecorded deletion with HEAD's content; it did not create a new commit.

## Explain the result

You should now be able to answer:

1. Why did the two-note commit leave three notes in the worktree?
2. Why did creating a branch leave the database unchanged?
3. Why could export inspect HEAD without changing application data?
4. Which operation brought the deleted row back?

Answers: commit used the staged snapshot; a branch is a pointer; export wrote an independent file; restore materialized HEAD at the tracked path.

These checks validate behavior. They do not require reading private index files, interpreting cache layouts, or measuring storage-directory size.

Continue with [merge conflicts](/docs/guides/merge-conflicts/) to try changes on both branches, or [remote sync](/docs/guides/sync-remotes/) to transfer recorded history.
