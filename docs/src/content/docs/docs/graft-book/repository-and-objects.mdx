**Where is my application version?**

The worktree contains the files your application opens. Graft keeps repository state in `.graft/` beside them.

```text
project/
├── app.sqlite
├── settings.json
├── attachments/
│   └── report.pdf
└── .graft/          Graft history, staging, storage, and recovery state
```

This is a physical directory tree. `app.sqlite` is one file. Its tables are logical contents inside that file.

Use repository commands to inspect or change history. Do not edit files inside `.graft/` as an application API.

## A commit names a complete version

Suppose commit C1 records one note and a paper theme. C2 records a second note and a dark theme.

The following diagram shows logical references, not directories. C1 and C2 are teaching labels; real commit IDs are content-derived hashes.

```text
main -- points to --> C2 -- parent --> C1
                      |
                      +-- tree: paths in this version
                           |
                           +-- app.sqlite: database snapshot
                           +-- settings.json: recorded file bytes
                           +-- attachments/report.pdf: external payload pointer
```

A **tree** maps paths to recorded content. A **blob** describes one path's content. A commit references its tree and parents. Existing objects are immutable: new content produces new objects.

Small text can be stored in its blob. Binary files, large text, and configured external files use an **external payload**: bytes stored separately and identified by content hash. A pointer can be present before those bytes have been downloaded.

## A branch names a commit

A **ref** is a mutable pointer. A branch such as `main` is a ref that moves when you commit.

```text
Before commit: main -> C1
After commit:  main -> C2 -> C1
```

Creating another branch at C2 does not copy the databases. It creates another pointer to the same version.

**HEAD** identifies your current position. Normally it names the current branch. A detached HEAD names a commit directly. Before the first commit, HEAD can name `main` even though that branch has no commit yet.

Inspect these relationships with:

```bash
graft log
graft show HEAD
graft branch
```

## The index selects changes to the current version

Outside a merge, the index stores staged differences from HEAD. A staged path replaces or removes that path in the next commit. Paths without staged entries keep their HEAD versions.

During a merge, it can also hold three versions of a conflicted path:

| Stage | Meaning |
| --- | --- |
| 1 | Base: common ancestor |
| 2 | Ours: local version |
| 3 | Theirs: incoming version |
| 0 | Selected result for the next commit |

An unresolved conflict blocks completion. A missing side can mean the path was deleted.

## Inspect the state that answers your question

| Question | Inspect |
| --- | --- |
| What does the application read now? | Worktree file or SQL query |
| What is staged? | `graft status` and `graft diff --staged` |
| What did I record? | `graft show HEAD`, history diff, or export |
| Which branch am I on? | `graft branch` |
| What remains unresolved? | `graft conflicts` |

Internal caches help Graft work faster. They do not define recorded versions. Refs, objects, staged state, and merge recovery records serve different purposes; do not treat the whole `.graft/` directory as a disposable cache.

See the [repository specification](/docs/specifications/) for object encoding, path normalization, and ref update rules.
