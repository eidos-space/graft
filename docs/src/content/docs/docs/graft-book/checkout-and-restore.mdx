---
title: 04 Checkout and Restore
description: Choose between download, export, and worktree replacement, and manage SQLite connections safely.
---

**Do I want to inspect a version or use it?**

To inspect an old database while keeping the application on its current version, **export** it to an independent path.

To make the application use recorded content, **restore** a path or **switch** branches. These operations can replace worktree files.

| Action | Where content goes | Effect on application files |
| --- | --- | --- |
| Hydration | Local Graft storage | Downloads missing content; does not replace tracked files |
| Export | An independent output path | Leaves the tracked database in place |
| Materialization | A tracked worktree path | Writes recorded content back to that path |

**Materialization** is Graft's term for turning recorded content into worktree files. It can happen during switch, checkout, restore, hard reset, pull, clone, and merge operations.

## Inspect first with export

From a repository that tracks `app.sqlite`:

```bash
graft export --source HEAD~1 --output ../previous.sqlite app.sqlite
sqlite3 ../previous.sqlite 'SELECT * FROM notes ORDER BY id;'
```

Choose a fresh output path outside the worktree so the exported file does not appear as a new application file. Export does not move HEAD or change the index.

## Restore a recorded path

After closing application connections to the affected database:

```bash
graft restore --source HEAD -- app.sqlite
graft sql --db app.sqlite "SELECT * FROM notes ORDER BY id;"
graft status
```

This restores the path from HEAD without moving the branch. Changes in that worktree path are replaced. The explicit `--source HEAD` matters: without a source, worktree restore uses staged content.

Unstaging has a different effect:

```bash
graft restore --staged -- app.sqlite
```

This resets the staged entry from HEAD and leaves the worktree database in place.

## Close connections before replacement

A database connection can keep referring to the old file after a replacement, even when it is idle. A writer lock check cannot manage your application's connection lifecycle.

Use this sequence:

```text
Pause new application writes
        |
Finish transactions and close affected SQLite connections
        |
Run the materializing operation
        |
Inspect its result and repository status
        |
Reopen connections to the resulting files
```

Graft checks SQLite replacement conditions and handles WAL sidecars. An active writer, busy WAL, invalid sidecar, or path collision can block replacement. Resolve the reported condition before retrying.

## One rename does not make a multi-file transaction

Graft uses temporary files and guarded replacement. Multi-path checkout can use backups and attempt restoration after failure. Each replacement is separate; an operating-system error can leave partial effects.

After failure, inspect `graft status`, returned path actions, and affected data. Reconcile the result before resuming application writes. Do not infer the whole operation's result from one file.

## Integrate using the operation's effects

The SDK's `operationMaterializesWorktree(name)` is a conservative pre-call gate: `true` means the operation can replace tracked paths for some inputs. The result's `worktree_paths` reports actual affected paths.

| Operation | Can replace tracked worktree files? |
| --- | --- |
| status, log, diff, fetch, add, commit | No |
| staged restore, mixed reset | No |
| switch, checkout, path restore, hard reset, pull, clone | Yes |
| merge planning (`planMerge`) | No; it may hydrate required data |
| merge apply, resolution, abort | Yes |
| export | No; writes to the independent destination |

“No” here means no replacement of tracked application files. Fetch still writes repository storage; commit still writes objects and refs.

Setting `worktree.materialize_sqlite = false` disables SQLite projection in ordinary checkout plans. Explicit resolution and ordinary artifacts can still write files. Use the operation gate to manage handles.

See [history and restore](/docs/guides/history-and-restore/) for branch and reset commands, and the [worktree specification](/docs/specifications/) for exact replacement rules.
