**One note, three places**

Your application stores notes in `app.sqlite`. It also reads `settings.json` and files in `attachments/`. Graft records selected versions of these paths together.

Start with three places:

| Place | Question it answers | What changes it |
| --- | --- | --- |
| Worktree | What is the application reading now? | SQLite transactions and ordinary file writes |
| Index (staging area) | What have I selected for the next version? | `graft add`, unstaging, and conflict resolution |
| History | What did I record as a version? | `graft commit` |

```text
Application writes
       |
       v
Worktree -- graft add --> Index -- graft commit --> History
   ^                                                  |
   |---------- restore or switch from history --------|
```

The arrows mean capture, record, or replace. They do not mean continuous synchronization.

If you add a note after `graft add`, the next commit contains the earlier staged database. The newer note remains in the worktree. If you push that commit, the remote receives the recorded version.

## What you should be able to predict

After reading this guide, you should be able to:

- say whether a command changes application files, staged state, or history;
- explain why saving a SQLite transaction does not create a Graft commit;
- choose between export, restore, fetch, and pull;
- identify what to inspect after a conflict or interrupted operation.

The [hands-on lab](/docs/graft-book/hands-on-lab/) lets you check these predictions with SQL queries and repository commands.

## A second layer stores database pages

A **repository commit** records an application version: paths, their contents, and parent commits. A **storage commit** records changed database chunks inside Graft's storage engine.

These are different records. One repository commit can contain several databases and files. Staging a database can create storage records before you create a repository commit. Branches point to repository commits.

You can use Graft without knowing storage log identifiers or page layout. The snapshot chapter introduces them only when they help explain reuse and reconstruction.

## Where to find exact rules

This guide explains the model. [Task guides](/docs/guides/track-databases-and-files/) give command sequences. [Specifications](/docs/specifications/) define exact contracts and limits.

Use the CLI and its JSON output, the Node.js SDK, or HTTP remote packages for integration. Internal storage keys, cache filenames, and Rust module boundaries are implementation details.
