**Which edits will the next commit contain?**

A SQLite transaction saves application data. `graft add` selects a snapshot. `graft commit` records the selected version in repository history.

These are three separate actions.

## Follow a note through the three actions

Assume HEAD contains one note.

| Action | Worktree | Staged database | HEAD |
| --- | --- | --- | --- |
| Insert and commit a second note with SQLite | Two notes | No staged change | One note |
| `graft add app.sqlite` | Two notes | Two-note snapshot | One note |
| Insert and commit a third note with SQLite | Three notes | Still two notes | One note |
| `graft commit -m "save two notes"` | Still three notes | Staged change cleared | Two notes |

The third note remains an unstaged change. Commit consumes staged content; it does not capture the live database again.

Run `graft add app.sqlite` again before committing if you want the third note included.

## Initialize, stage, review, record

`graft init` creates `.graft/` and an initial branch position. It does not create a database or automatically track existing files.

For an existing application directory:

```bash
graft init
graft status
graft add app.sqlite
graft add settings.json
graft diff --staged
graft diff --rows --staged app.sqlite
graft commit -m "save notes and settings"
graft status
```

Review the staged diff before committing. Afterward, status tells you whether newer worktree changes remain.

Use `graft add --all` to stage eligible additions, modifications, and deletions together. See [tracking databases and files](/docs/guides/track-databases-and-files/) for ignore rules and path selection.

## How files meet in one commit

A database takes the consistent-snapshot path. An ordinary file takes the exact-byte path.

```text
app.sqlite ------ consistent capture --> database snapshot --+
settings.json --- read file bytes -----> file blob -----------+--> index
report.pdf ------ read file bytes -----> external pointer ----+
                                                               |
                                                               | commit
                                                               v
                                                      application version
```

A commit combines the HEAD tree with staged replacements and deletions. Unstaged paths keep their recorded HEAD versions.

The common commit is a version boundary. It does not make independently captured paths one transaction; your application must coordinate related writes if it needs that guarantee.

## Why a branch moves last

Graft writes the required immutable objects before moving the branch to the new commit. Otherwise, the branch could name a version whose contents were not available.

A failure before the ref update can leave unreachable objects. The branch still identifies the previous version. If a later step fails, inspect status and history before deciding whether the commit happened.

This ordering does not guarantee full crash durability. Some object, index, and merge-record writes are direct writes, and version 1.0 does not promise an end-to-end `fsync` contract. Reflog append and ref replacement are separate operations.

## Check your prediction

You stage two notes, then insert a third, then commit. How many notes are in HEAD?

**Two.** Export HEAD and query it to verify. The [lab](/docs/graft-book/hands-on-lab/) performs exactly this experiment.

Commit writes local history. Uploading that history requires a separate [push](/docs/graft-book/remotes-and-recovery/).
