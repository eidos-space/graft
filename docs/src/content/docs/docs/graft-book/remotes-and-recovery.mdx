title: 06 Remotes and Recovery
description: Distinguish push, fetch, pull, and clone, then identify the state to inspect after a failure.

**Which version reaches the remote?**

A remote stores recorded repository history and the content needed to read it. It does not watch your application's live database.

| Action | Local history | Remote history | Worktree |
| --- | --- | --- | --- |
| SQLite transaction | Unchanged | Unchanged | Changes database |
| Add and commit | Records selected version | Unchanged | Keeps current files |
| Push | Keeps local version | Publishes recorded history | No replacement |
| Fetch | Downloads history and updates remote-tracking refs | Read | No replacement |
| Pull | Fetches, then merges | Read | Can replace files |
| Clone | Creates local repository from remote | Read | Writes checked-out files |

An uncommitted note does not become remote history just because you push.

## Try a filesystem remote

After creating a repository with a commit on `main`, choose an absolute path for a separate test remote:

```bash
graft remote add origin fs:///tmp/graft-book-remote
graft push origin main
graft ls-remote origin
```

Use a fresh remote path for an isolated test. Graft also supports object storage and HTTP remotes; see [remote backends](/docs/remotes/).

A remote is an additional copy of history. Backup still needs its own retention, access, and recovery policy.

## Push publishes content before the branch

A remote branch must identify a version whose required content has been published.

```text
Upload database storage + external file payloads
                       |
Upload repository objects that describe the version
                       |
Conditionally update the remote branch
```

The final update uses **compare-and-swap (CAS)**: update the branch only if it still has the value observed at the start.

If another client moved the branch, the update fails. Uploaded immutable content may remain unreachable, but the branch does not expose the proposed incomplete publication.

Force push relaxes the fast-forward rule. It still checks the expected remote value with CAS.

## Fetch is a chance to inspect; pull also applies

Fetch downloads the selected history and updates a remote-tracking ref such as `origin/main`. It does not move your current branch, change the index, or replace tracked files.

```bash
graft fetch origin main
graft log
graft diff HEAD origin/main
```

The last command compares your version with the fetched remote position.

Pull performs fetch, merge planning, and merge application. It can fast-forward, enter conflict state, and replace databases. Close affected application connections first.

Metadata may arrive before every historical page or external payload. A later read can hydrate missing content. “I can see the commit” and “all its bytes are local” are separate observations.

Clone initializes a new repository, obtains remote history, sets tracking, and checks out files. It does not silently overwrite a non-empty destination.

## A lost response leaves the outcome unknown

If a branch-update request was sent but its response was lost, the server may have applied it. Timeout or cancellation does not prove it did nothing.

Read the remote branch again:

| Observed value | Meaning |
| --- | --- |
| Intended new commit | The intended branch position is present |
| Original commit | The intended update is not reflected in the current ref |
| Another commit | Another writer or divergence must be reconciled |

Fetch current state and make a new plan when needed. Do not blindly publish a different successor.

## Recover from the state that remains authoritative

| Failure | Inspect first |
| --- | --- |
| Capture or stage fails | Worktree and existing staged state |
| Commit reports failure | Current ref, history, and index |
| Checkout or restore stops partway | Status, returned path actions, and affected files |
| Merge is interrupted | Index conflict stages and resolution journal |
| Push loses its response | Remote branch value |

Stop application writes and close affected SQLite connections when recovery can replace files. Inspect `graft status --json`, complete or abort an active merge, and reconcile uncertain remote results before resuming writes.

Missing or corrupt content must be reported. A missing page is not a zero page; a missing payload is not an empty file.

## Cleanup is a separate operation

SQLite storage GC, external-payload pruning, and repository-object maintenance have different roots and limits. The 1.0 surface has no public loose-object GC.

Do not delete internal storage to fix an unresolved merge or uncertain push. First recover a valid version; then use the appropriate maintenance command.

Exact publication and recovery rules are in the [remote and repository specifications](/docs/specifications/).
