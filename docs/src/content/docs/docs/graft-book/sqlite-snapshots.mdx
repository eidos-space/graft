**What does a database snapshot contain?**

A **snapshot** is one consistent, committed SQLite database state. It can be restored as an ordinary SQLite file.

Suppose your application inserts a note and commits its SQLite transaction. In WAL mode, that note may be in `app.sqlite-wal` rather than the main `app.sqlite` file. Copying only the main file can miss it.

When you run `graft add app.sqlite`, Graft captures a private, consistent database image. The capture includes committed WAL frames and excludes uncommitted transactions. You do not need to checkpoint manually.

```text
app.sqlite + committed app.sqlite-wal content
                   |
                   | consistent capture
                   v
          private database image
                   |
                   | store changed chunks
                   v
          staged snapshot
```

The private image is temporary. Staging does not replace the application's database.

Each database capture is consistent. A commit containing several databases and files does not create an application-wide transaction across them. Coordinate application writes when those paths must represent the same checkpoint.

## How Graft reuses unchanged content

Graft divides the captured image into 4 KiB storage chunks. It compares them with the staged or committed baseline and records changed chunks.

This simplified example shows chunk reuse. Letters stand for byte contents, not SQL rows.

```text
Snapshot A: [A][B][C][D]
Snapshot B: [A][B][X][D][E]

New content for B: chunk 3 = X, chunk 5 = E
Reused content:    chunks 1, 2, and 4
```

Snapshot B still represents a complete database. Reading it combines new chunks with unchanged chunks from earlier storage records. Restoring it reconstructs the file.

Think of a loose-leaf book: a later edition can keep unchanged pages and replace others. The first capture needs all chunks. Later captures can reuse unchanged content; a snapshot is a description of a complete state, not a standalone file containing only the changes.

For the example above, reading B selects these contents:

| Position | Content selected for B |
| --- | --- |
| 1, 2, 4 | Unchanged A, B, D from earlier storage |
| 3 | Replacement X |
| 5 | New content E |

Selecting B does not change A. Stored contents are immutable, and each snapshot selects its own contents and logical size. Restoring B reconstructs the complete SQLite file; the application then opens that ordinary file. It does not replay the SQL that produced B.

One row edit can affect several chunks because SQLite also maintains indexes and metadata. Directory size includes storage overhead; it does not measure the number of row changes.

## Two meanings of “page”

SQLite has its own physical page size. Graft storage chunks are always 4096 bytes. An 8 KiB SQLite page occupies two Graft chunks.

The chunk boundary determines storage reuse. It does not determine row identity or merge decisions. Logical diff and merge interpret SQLite tables and schemas separately.

## From stored chunks to understandable changes

Suppose two captured versions contain a `projects` table:

| Record | Snapshot A | Snapshot B |
| --- | --- | --- |
| `id = 1` | `budget = 100` | `budget = 120` |
| `id = 2` | Absent | `budget = 200` |

Physical comparison identifies changed storage content. Row comparison identifies one update and one insertion. Those are different questions: several rows can occupy one SQLite page, and one row change can affect several pages.

```bash
graft diff HEAD~1 HEAD app.sqlite
graft diff --rows HEAD~1 HEAD app.sqlite
```

The first command identifies a changed path. The second also explains supported database changes. Row analysis aligns records by identity: `rowid` for ordinary rowid tables, or the declared primary key for `WITHOUT ROWID` tables. An `INTEGER PRIMARY KEY` such as the example's `id` aliases the rowid.

Schema, opaque changes, and limitations accompany the row result where applicable. An empty row diff is not evidence that all database content is unchanged. See [diff rows and files](/docs/guides/diff-rows-and-files/).

## Capture comes before recording history

`graft add app.sqlite` captures and stages a database version. `graft commit` records that staged version; it does not capture the live database again. Writes made after staging remain outside the commit until another `add`.

Storage chunks answer “how can this version be reconstructed?” Repository commits answer “which application checkpoint is this?” SQLite diff answers “what changed?” Keep these three roles separate when presenting history in an application.

## Storage coordinates, when you need them

A storage commit records changed chunks and the resulting chunk count. Its coordinate is `(LogId, LSN)`: a log identifier and a sequence number within that log.

LSNs are ordered only inside one log. LSN 3 in two different logs does not identify the same version or establish their chronological order.

A snapshot descriptor records a volume, logical size, ordered log ranges, and expected storage-commit hashes. The ranges describe how to find each chunk. A volume is a lineage handle; the immutable descriptor identifies the database state referenced by history.

Use repository commits, branches, and tags in application history. Reserve storage coordinates for storage debugging.

## What happens when nothing changed?

If chunks and logical size match the baseline, Graft can reuse the snapshot without appending a storage commit.

When a database shrinks, older stored chunks may remain outside the new logical size. Truncation is not secure erasure. Unreachable storage data is a separate garbage-collection concern.

The current capture implementation uses SQLite online backup, with a guarded file-clone optimization for suitable macOS rollback-journal databases. Both paths must capture consistent committed state.
