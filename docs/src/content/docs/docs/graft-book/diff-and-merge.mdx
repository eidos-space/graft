**What changed, and can two changes combine?**

A path diff answers “which files changed?” A SQLite logical diff answers “which supported rows and schema entries changed?”

From a repository with two commits:

```bash
graft diff HEAD~1 HEAD
graft diff --rows HEAD~1 HEAD app.sqlite
graft diff --json --rows HEAD~1 HEAD app.sqlite
```

The first command locates changed paths. The others expand database changes. Diff does not change refs, staged state, merge records, or tracked worktree files.

## An empty row list is not “unchanged”

A database can change because of schema, indexes, virtual tables, or other content that is not an ordinary row edit.

Read `logical_status`, schema changes, opaque changes, capabilities, and limitations together. **Opaque** means Graft cannot fully interpret that changed surface. Keep that limitation visible in an application review UI.

Ordinary tables normally use signed 64-bit `rowid` identity. `WITHOUT ROWID` tables use their declared primary key, including composite keys. Generated columns can appear in output but are excluded from ordinary replay.

Supported layouts can be read directly. Other supported cases use an isolated temporary compatibility database and report `materialized_compat`. That temporary database is not the application worktree.

## Merge compares three versions

Suppose two branches start from the same notes:

| id | Base body | Ours body | Theirs body | Result |
| --- | --- | --- | --- | --- |
| 1 | first | first, edited locally | first | Local edit |
| 2 | second | second | second, edited remotely | Incoming edit |

Each side changed a different row. A supported, validated merge can keep both edits.

If both sides change row 1 incompatibly, Graft reports a conflict so you can choose a result.

```text
         Base: common ancestor
          /                 \
 Ours: local HEAD       Theirs: target revision
          \                 /
             merge result
```

This diagram describes ancestry and inputs. Merge uses row and schema meaning, not a comparison of storage LSN numbers.

## Check the history relationship first

| Relationship | Outcome | What happens |
| --- | --- | --- |
| Target is already in local history | Up to date | No change |
| Local HEAD is an ancestor of target | Fast-forward | Move to target and check out its content |
| Both sides have new commits | Three-way | Combine changes or enter conflict state |

Unrelated histories use an empty base and report `merge_base = null`.

The SDK separates read-only `planMerge` from `applyMerge`. The plan token binds the observed inputs and policy. Apply rejects a stale plan rather than applying it to changed state.

## Know the limits of automatic merge

Graft attempts row/schema-aware merge for compatible SQLite inputs. It builds a private candidate, applies safe changes in a transaction, and validates the result, including constraints and foreign keys.

Incompatible row edits, conflicting schemas, unsupported SQLite surfaces, and modify/delete cases can require resolution. Ordinary files use conservative whole-path conflicts. Schema and internal resolvers are a bounded built-in set; they are not arbitrary SQL hooks.

“Different rows” is a useful prediction, not an unconditional guarantee. Schema compatibility and constraints still matter.

## Complete or abort a three-way merge

For branches you have created and recorded:

```bash
graft --db app.sqlite merge feature/notes
graft status
graft --db app.sqlite conflicts --json
```

Close affected application connections before materializing operations.

If the three-way merge has no unresolved conflicts, complete it:

```bash
graft merge --continue -m "merge notes"
```

A fast-forward has already moved to the target and does not need a merge continuation.

If conflicts remain, inspect and resolve them with the [conflict guide](/docs/guides/merge-conflicts/), then continue. To discard the active merge result and restore the pre-merge version:

```bash
graft merge --abort
```

Conflict state includes index stages and a durable resolution journal. Restarting the application does not itself resolve a conflict. After interruption, inspect that state and continue resolving or abort.

Successful continuation creates a commit with both Ours and Theirs as parents. Abort clears merge records only after restoration succeeds.
